La tesis

Hacer un agente de IA es el 10% del trabajo

Cualquiera arma un agente en un notebook. El FDE es quien lo pone frente a un cliente, decide qué hace el modelo y qué no, mide cuánto cuesta cada conversación y responde cuando algo se rompe un lunes a las 3 de la mañana. Antes de empezar

¿Qué es un harness?

Un harness es todo el código que rodea al modelo y convierte lo que el modelo dice en acciones útiles, seguras y medibles. El modelo solo recibe texto y devuelve texto. No ejecuta nada, no recuerda nada entre llamadas y no sabe cuánto cuesta. Todo eso lo hace el harness.

La palabra viene del inglés y significa arnés. Un caballo tiene la fuerza, pero sin arnés no tira de ningún carro: la fuerza no llega a ningún lado, o llega a donde no debe. El arnés no le agrega fuerza; la dirige. Con un modelo de lenguaje pasa lo mismo.

Un ejemplo de CLARUS

Cuando PRESTO pregunta "¿Te armo el presupuesto con esto?", esa frase la escribe el modelo. Pero que el presupuesto no se cree hasta que el cliente diga que sí lo garantiza el harness. Si dependiera solo del modelo, un día se lo saltearía.

Lo que un harness no es

  • No es un prompt más largo: un prompt pide, el harness garantiza.
  • No es el modelo: si mañana cambiás de modelo, el harness queda.
  • No es lo mismo que un framework: un framework es un harness genérico. Uno a la medida está hecho para un proceso y un cliente.

Y Astromesh, ¿qué es?

Un harness que se volvió runtime: las piezas de esta tabla, hechas configurables para que cada agente nuevo no las reescriba. Vamos a construir las nuestras a mano para entender qué resuelve cada una antes de usar algo hecho.

En software el término ya existía: un test harness es el código que rodea a una pieza para ejecutarla y observarla. La idea es la misma.

La pregunta que enseñamos a hacer

¿Construir, adoptar o comprar? Se adopta lo que es estándar y no te diferencia (MCP, OpenTelemetry, pgvector). Se construye lo que define cómo trabaja tu cliente: las compuertas, el costo por unidad, el canal. Se compra cuando el cliente ya vive en esa nube.

Lo que casi nadie trae

La mayoría de los frameworks resuelve bien el loop y las herramientas. Lo que el FDE termina construyendo solo es el 90% de la tesis: canales con entrega garantizada, aislamiento por cliente, techo de gasto, facturación y operación.

M1~25 min

El nacimiento de Astromesh

El 6 de marzo de 2026 se aprobó un documento de diseño con una tesis: cualquier vertical de negocio puede definir, desplegar y operar agentes desde configuración, sin reescribir código. Astromesh no es un wrapper de LLM. Es un runtime de agentes con identidad, estado, memoria, permisos, herramientas y patrones de orquestación. La comparación que guía todo es la de Kubernetes con los contenedores.

El problema que resolvía

Cada equipo reconstruía las mismas seis piezas: proveedores, herramientas, memoria, prompts, seguridad y orquestación. Y terminaba con un framework propio, atado a un solo proveedor. Son las seis piezas que vamos a construir.

Las decisiones del día uno

  • Python + FastAPI, agentes en YAML + Jinja2
  • Postgres para todo (pgvector por defecto)
  • Ollama por defecto, vLLM para alto rendimiento
  • MCP + herramientas internas, OpenTelemetry desde el inicio

Línea de tiempo

  • Día 1: router con 6 proveedores, ReAct, 3 tipos de memoria, RAG, MCP, guardrails, WhatsApp. v0.1.0 → v0.3.0 el mismo día
  • Día 3: extensiones en Rust, gobernanza, CI
  • Día 4: diseño de Helm y de la malla de nodos
  • Hoy: v0.63.0, 14 componentes

M2~45 min

Anatomía de un agente: construir el loop

Un agente es un loop: el modelo lee el contexto, decide si llama a una herramienta, el harness la ejecuta y le devuelve el resultado, hasta que el modelo responde. Lo escribimos desde cero y vemos que todo lo demás se cuelga de ese loop.

consulta→guardrails de entrada→memoria→RAG→prefetch→prompt→patrón→router de modelos→tools→guardrails de salida→persistir

El pipeline completo de Astromesh. Hoy construimos el centro: prompt, patrón, modelo y tools.

Construimos en vivo

  • El loop ReAct con un tope de iteraciones.
  • Un registro de herramientas con su esquema para el modelo.
  • Memoria conversacional con ventana deslizante.
  • Un presupuesto de tokens para el historial, calculado desde la ventana del modelo.
  • El agente definido como datos (YAML), no como código.

Contraste con Astromesh

  • 7 patrones sobre la misma base: ReAct, PlanAndExecute, ParallelFanOut, Pipeline, Supervisor, Swarm, Glyph
  • Tools internas, MCP, webhook, RAG y otro agente como herramienta
  • Memoria conversacional, semántica y episódica
  • El historial viaja como mensajes, recortado al presupuesto o resumido por el rol summarizer
apiVersion: astromesh/v1
kind: Agent
metadata: { name: vendedor }
spec:
  model: { default: { model: kimi-k2.6, context_window: 131072 } }
  orchestration: { pattern: react, max_iterations: 8 }
  tools: [ praxis, crear_presupuesto, consultar_tecnico ]
  memory: { conversational: { strategy: summary, max_turns: 40 } }
  prompts:
    system: Sos el vendedor de mostrador de PRESTO...   # estable: se cachea
    context: "{{ knowledge }} {{ prefetch.stock }}"     # cambia por consulta: va al final

M3~35 min

Un agente trabajando, en CLARUS

Con el loop recién escrito, miramos un agente en producción y anotamos todo lo que a nuestro harness le falta. CLARUS lleva un negocio desde la entrevista hasta el proceso automatizado, y sus agentes atienden por WhatsApp, Telegram, Instagram y webchat. El caso es PRESTO, un vendedor de mostrador: un vendedor que arma presupuestos y un técnico de solo lectura que el vendedor consulta como herramienta.

Lo que vamos a ver

  • El vendedor delega una pregunta técnica al sub-agente.
  • Antes de escribir, pide confirmación: "¿Te armo el presupuesto con esto?"
  • El presupuesto se crea entero en una sola transacción.
  • El mensaje entra por Herald y el agente corre en Nexus.

Lo que medimos

  • Sesión real: 5 invocaciones, USD 0,084
  • Replay: predijo USD 0,0862, 2,6% de error
  • 12 de 12 corridas cumplidas, 0 confirmaciones falsas
  • Plan: USD 300/mes con 84% de margen

Lecciones de producción

  • "El LLM no calcula dinero": el costeo vive en código determinista.
  • Un modelo retirado por el proveedor dejó mudos a todos los agentes de dev sin una sola alerta roja.
  • El RAG nunca consulta sin filtro de tenant.

M4~45 min

El harness a la medida: compuertas y capas

Un harness es todo lo que rodea al modelo para que su trabajo sea útil y seguro. La regla: cada cosa en su capa. El modelo razona; lo demás es trabajo determinista y no debería costar tokens ni segundos.

Sumamos al harness

  • Confirmación: las herramientas que escriben piden un sí humano, y una llamada anidada no puede darse permiso.
  • Guardrails: PII, largo máximo y límite de costo por corrida.
  • Prefetch: las búsquedas que el agente siempre hace corren antes del modelo.
  • Orden del prompt: lo estable primero y lo que cambia por consulta al final, para que el proveedor cachee.
  • Router con fallback: si el modelo falla o lo retiran, el agente no queda mudo.
  • Libro de costos: tokens y dólares por corrida.

Contraste con Astromesh

  • Prefetch en un auditor de CLARUS: ~5 s por viaje al LLM contra ~55 ms de búsqueda.
  • Modo propose: la escritura se registra en lugar de ejecutarse.
  • Credencial por corrida que muere con la corrida.
  • Router por costo, latencia o calidad, con circuit breaker y un modelo por rol.
  • Siete módulos en Rust en los caminos calientes.

Caso de estudio: la hipótesis que falló

Glyph nació para ahorrar tokens: el modelo escribe un programa en lugar de una llamada por turno. Lo medimos con tres modelos y costó entre +164% y +2839% más que ReAct, porque el modelo escribía el programa en cada corrida. Lo documentamos y cambiamos el diseño: el modelo escribe el programa una vez, una persona lo revisa y el runtime lo ejecuta sin llamar al modelo.

Caso de estudio: la memoria que prometía y no cumplía

Auditando el contexto encontramos que las estrategias de memoria del YAML no hacían nada: los turnos se guardaban sin contar tokens, el resumen nunca se generaba, el presupuesto era un 4096 fijo y el historial no llegaba al modelo como mensajes. Los agentes solo recordaban si su prompt de sistema recorría la conversación, y eso cambiaba el primer mensaje en cada turno.

El arreglo: la ventana se resuelve por modelo al cargar el agente (declarada, de Ollama o de LiteLLM), se descuentan el sistema, las tools y la respuesta, y el historial entra como mensajes. Si la ventana es desconocida no se recorta en silencio: se avisa.

El orden del prompt decide el caché

Kimi cachea por prefijo, sin marcar nada. Medido: hasta 86–88% del prompt desde caché si el prefijo no cambia. Pero el RAG y el prefetch vivían en el prompt de sistema, así que el prefijo se rompía en cada consulta.

system→tools→historial→contexto + consulta

Todo lo que va antes del último mensaje es prefijo estable. El turno se guarda sin el contexto, así el RAG no se acumula en la memoria.

M5~40 min

De un agente a un ecosistema agéntico

Un agente solo no atiende a un cliente. Hace falta que otros agentes lo ayuden, que un canal le traiga mensajes, que cada cliente esté aislado y pague lo suyo, y que alguien vea qué pasó en cada corrida. Llevamos el harness de una pieza a un sistema.

Sumamos al harness

  • Un agente como herramienta de otro (el vendedor y su técnico).
  • Ejecución en paralelo de dos especialistas y una síntesis.
  • Un canal de entrada: webhook o webchat.
  • Tenant por credencial y techo de gasto.
  • Trazas por corrida.

Lecciones de escala

  • CI que se rompe por calendario: una versión nueva de ruff dejó rojo cualquier PR sin cambiar código. Desde entonces los lockfiles se versionan.
  • Ningún paquete del nodo había corrido fuera de CI hasta que se probó en máquinas limpias.
  • Versiones independientes por paquete: solo se sube lo que cambió.

El oficio: cotizar, operar y responder

Un agente que no se puede cobrar ni operar es un experimento. Cerramos con el trabajo que nadie cotiza: costo por unidad, margen, límites de gasto por cliente, y la pregunta de quién lo opera el lunes a las 3 de la mañana.

El método de CLARUS

  • Costo de LLM por unidad de trabajo (un presupuesto, una consulta)
  • Margen objetivo del 70%
  • Techo de gasto mensual por tenant
  • Cada corrida registrada con su consumo

Práctica final

Cada participante presenta su harness funcionando, el costo por unidad medido en su máquina y en la nube, y el precio que le pondría. El foro hace de cliente.

Basado en la realidad

Qué no vamos a decir

  • Juez de acciones (spec.judge): es un diseño del 2026-10-02, no está implementado. Si aparece, se presenta como lo que viene.
  • Producción de CLARUS: los docs se contradicen sobre si prod existe. Las cifras de PRESTO son de dev; se dicen así.
  • Coreografía autodisparada: lo que existe es el encadenamiento declarativo (spec.chain.on_complete, desde v0.38.1). La coreografía distribuida entre nodos está diferida.
  • Frameworks de terceros: la comparación sale de su documentación pública, no de mediciones nuestras (salvo Google ADK, medido con Prisma). Se revisa contra la versión vigente de cada uno antes de la clase.
  • Otras nubes: solo tenemos medido GCP. AWS o Azure se presentan como prueba nueva, no como resultado.
  • Presupuesto de contexto y prompts.context: están en develop desde el 2026-10-05, todavía sin release. El 86–88% de caché se midió el 2026-09-04 con prefijo estable; la ganancia de este cambio sobre la flota aún no está medida. OFFICIUM y CLARUS siguen recorriendo la conversación en el prompt de sistema hasta que se actualice su generador.
  • Compresión y optimización de prompts: LLMLingua, DSPy y spec.context son el siguiente subproyecto, no existen hoy.
  • Número de clientes: no lo tenemos medido; no se menciona.
